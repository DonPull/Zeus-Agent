# Benchmark execution environment

Status, 6 November: the user's normal restart activated Sandbox and the hypervisor,
with no component restart pending. Two consecutive protocol-2 guest probes passed
all seven boundary/fresh-storage checks and closed their owned host processes.
A pinned public bundle now runs the real Zeus app, Python and managed Chromium
against a synthetic guest-local fixture. Mission orchestration and the separate
grader remain incomplete; this is not a validated full executor.

The current host is Windows 11 Pro 23H2 with firmware virtualization and SLAT,
and the Windows Sandbox component was initially absent. The reviewed prerequisite is
the included PowerShell script. Its default prints a plan and writes a project
receipt without changing Windows. The explicit `-Enable` mode requires an
administrator and calls only the named optional-feature operation with
`-All -NoRestart`. It does not elevate itself, reboot, change policies, create
accounts or add firewall rules. Exit 2 means the operation needs a manual restart.

After user approval, an administrator can run:

```powershell
powershell -NoProfile -ExecutionPolicy RemoteSigned -File scripts/eval_harness/sandbox/enable_windows_sandbox.ps1 -Enable
```

[Microsoft's installation instructions](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install)
document the administrator operation and possible restart. The newer 24H2 CLI is
not required. Do not automatically disable existing virtualization dependencies
as cleanup: they may serve other software.

Enabling the OS feature is not proof that the benchmark is isolated. Remaining
work includes the runtime bundle, restricted mappings/egress, actor/export and
separate executable-grader protocols, failure controls and actual guest probes.
No actor-created executable may run on the host while those gates are incomplete.

## Prepared boundary probe

`node scripts/eval_harness/sandbox/probe.js` prepares a fresh, ignored session
under `.zeus/evaluations/sandbox-sessions`. It does not launch Windows Sandbox.
The generated `probe.wsb` uses Microsoft's documented configuration: networking,
vGPU and clipboard/audio/video/printer redirection disabled, Protected Client
enabled, 4096 MiB memory and exactly two disjoint mappings. Input is read-only;
output is writable. The repository, credentials and private sentinel are not
mapped. The guest script checks input readability/write denial, the unmapped
sentinel and absence of active non-loopback network interfaces.

After confirming OS readiness, schedule an actual visible Sandbox launch
with the user. Do not launch every prepared historical session: choose a fresh
one generated by the current code. No physical keyboard/mouse input is needed.
Do not silently loosen settings if the OS rejects this configuration; retain
the failure and investigate the supported boundary.

`node scripts/eval_harness/sandbox/probe.js --inspect <session-directory>`
checks bounded result bytes, identity, unchanged configuration/input/sentinel
hashes and declared output names. It rejects links, device names, path traversal,
oversize and extra files. Even consistent guest claims return exit **2** and
`isolation_validated:false`; invalid/failed probes return nonzero. A JSON file
does not prove a guest launched or terminated, and cannot unlock model dispatch.
The actual OS lifecycle, actor/grader runtimes, cleanup, resource bounds and
provider/fixture transport still require implementation and guest validation.
CPU and writable-mapping disk quotas are not claimed.

## Explicit launch and cleanup controller

After notifying the user about the potential window, run a fresh prepared session:

```powershell
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File scripts/eval_harness/sandbox/run_probe.ps1 -Mode Run -SessionDirectory "<absolute prepared session directory>"
```

The controller holds a host-slot mutex, rejects another open Sandbox, records the
launcher/client PIDs and exact process-handle creation times, waits up to the
declared deadline, inspects guest data and closes only those owned processes.
It never persists the raw WindowsSandboxClient command line, which contains an
ephemeral guest credential. Each lifecycle receipt has a unique filename; failed
receipts remain retained. `-Mode Cleanup` can recover a proven owned session.
It refuses name/creation-time mismatches and never kills by process name.

Cleanup uses the owned client process handle; the observed launcher then exits.
That is partial lifecycle evidence, not independent HCS disposal certification.
The reviewed observations live in
[the probe record](../../../docs/benchmarks/sandbox-probes-20261106.json).
Protocol 2 also creates an unmapped guest-only marker and requires it to be absent
on the next fresh guest. The guest runtime inventory found no Python, Node or
WebView2. `prepare_runtime.py --catalogue` retains Microsoft's public metadata;
`--catalogue-from <retained-page.html>` parses it offline without JavaScript
execution. Neither mode downloads or runs a runtime installer.

## Pinned synthetic runtime check

Explicit `prepare_runtime.py` modes download one exact Microsoft x64 cabinet,
verify its retained hash, expand it using Windows `expand.exe`, and verify the
runtime's Microsoft signature/version. `--build-bundle <verified-webview-directory>`
copies selected public dependencies, the evaluation executable and built frontend.
It excludes user profiles, the repository, credentials, global site packages and
Python startup customizations. Every copied file has a size/hash inventory.

The current bundle pins Python 3.11.0, Node 22.13.1, Playwright 1.62.0, Chromium
151.0.7922.34, WebView2 157.0.4341.42 and signature-verified Microsoft C++ libraries
14.51.36247.0. The latter include MSVCP140.dll, required by greenlet; no runtime
installer runs on the host. These versions describe this checkpoint, not an
automatic upgrade policy.

`probe.js --runtime-bundle <owned-bundle-directory>` adds one readonly public
runtime mapping. The guest copies dependencies locally and verifies their hashes
before execution. Small trusted control scripts remain separate readonly inputs.
The elevated Sandbox account needs a guest-only, per-executable HKLM WebView2
debugging policy; no host registry setting changes. The check uses the real
bridge, normal policy, a bounded synthetic provider and an actual local browser
navigation. It requires two mock requests, known usage, exact dependency versions,
successful navigation and zero remaining owned browser processes.

This is a scripted runtime check with **zero hosted inference requests**, not a
capability score. Its JSON still cannot certify isolation. Live provider wiring,
all-mission fixture/artifact transport, isolated actor integration and remaining
resource/lifecycle gates remain open.
Keep failed probes and their hashes alongside the successful receipt.

## Synthetic host/guest file transport

Add `--transport-smoke` when preparing a runtime probe to move the fake provider
and website fixture to the host. The guest retains networking disabled. Its
loopback proxies exchange bounded data files with a trusted host broker. This
broker supports only POST `/chat/completions` for `phase1-mock` and GET `/` for
the synthetic fixture. It has no provider credentials, external HTTP client,
shell command or arbitrary-URL interface.

The protocol permits 32 messages, 1 MiB decoded bodies, 2 MiB exchange files and
16 MiB aggregate exchange bytes. Fresh nonces, exact fields, declared routes,
immutable request hashes and a host-private receipt bind every request/response.
The guest cannot write the input mapping. Host replies fill empty files prepared
before launch; length/hash/completion frames reject partial reads. An actual WSB
readonly mapping held rename locks, so response publication avoids rename.
Provider operations are never repeated to recover a publication failure.

The controller retains the broker's exact process handle and creation time,
checks its real exit code, and tears down only its owned processes. Read-only
inspection verifies the protected receipt against all exchange bytes, counts and
identities. A matching guest success message alone cannot satisfy this check.

`--transport-smoke --deny-test` deliberately writes an undeclared external route
from inside the guest. Its **expected** outcome is a failed probe, zero host
request handlers and successful owned-process cleanup. It must never be counted
as a successful model mission. Both actual positive and negative controls are
retained with the earlier publication/exit-check failures. No paid inference is
enabled by these modes. Core live dispatch remains unavailable.

## Separate known-control grading guest

`probe.js --runtime-bundle <owned-bundle-directory> --grading-smoke` prepares a
separate fresh guest with a readonly packet of existing C01/C02/C03/D02 graders,
public fixtures and twelve exact known controls. The packet is at most 1 MiB,
128 files and 1 MiB per decoded file; no user-selected program path is accepted.
The guest checks packet file hashes, runs the same outcome probes and retains
full assessments in `grader-evidence.json` (at most 2 MiB). The host checks its
hash, expected source identities, every reference criterion and every negative
outcome. A runtime success label alone is insufficient.

The dashboard grader uses the pinned `playwright-core` SDK and full Chromium
channel. No provider connection, API key, repository mapping or physical input is
needed. This mode validates only known controls and leaves the untrusted host
execution guard and core live-dispatch gates unchanged.

## Generated-submission grading

`node scripts/eval_harness/grade_submission.js --mission C01 --submission
<export-directory> --runtime-bundle <owned-bundle-directory>` prepares a bounded
snapshot without executing submitted code. Add `--run` explicitly to launch a
fresh Windows Sandbox. C01, C02, C03 and D02 are supported. Artifacts are limited
to declared names, 2 MiB per file and 8 MiB per packet; links and device paths
are rejected. Reference solutions are omitted from the guest packet.

The trusted controller creates a disposable non-admin account for candidate
programs. Grader files, private credentials, controller memory and the copied
runtime are protected from that account. Each candidate Python process starts
behind an activation gate in an owned Windows job; normal descendants and
timeouts are tested. Cleanup disables the account and checks exact token SIDs
for remaining candidate processes before signing a result.

Actual experiments found that WSB mapped folders remain accessible to the
candidate account despite local ACL restrictions. Consequently mapped output
JSON is never trusted on its own: the host pins a fresh Ed25519 public key before
acknowledging candidate startup, then verifies the signed job/nonce/packet and
assessment. A real submitted program that replaced the result file was rejected.
Raw assessments remain Node JSON; PowerShell receives metadata only, including
when a valid assessment contains an empty property name.

These controls validate this grading adapter, not a complete isolation
certificate. Independent HCS disposal, CPU and writable-mapping disk quotas
remain unvalidated. The full core live driver is still gated; this CLI neither
calls a provider nor enables paid dispatch.

## Host provider relay

`node scripts/eval_harness/provider_preflight.js` prints the frozen provider
binding without network or credential access. Explicit `--check` makes one
authenticated GET `/models` using the existing local Abacus key; no POST or
inference occurs. A fresh ledger is retained under `.zeus/evaluations/provider-preflight`.

The reusable relay accepts only Abacus `gpt-6.1-terra`, low effort, Chat payloads
and supplied inline images. Its fixed-route standard-library Python worker reads
the production Windows keyring entry and returns HTTP data only; the credential
does not enter Node, argv, environment, guest files or logs. Redirects are never
followed. Local tests use an explicit IPv4 loopback origin and dummy key.

Every attempted paid request receives a durable host reservation before dispatch.
One request may be in flight; request caps, output caps, wall deadlines and
explicit serialized-byte token estimates are enforced. Estimates are not exact
tokenization or a monetary ceiling. Raw provider usage/cache fields are retained;
unknown usage stops further dispatch. No automatic retry, model/effort fallback
or reset of an existing ledger is allowed. A file-publication failure retains
the completed paid call and cannot send it again.

Responses use the existing buffered file framing; per-token delivery timing is
not preserved. The relay is not yet connected to the isolated mission actor and
does not unlock the core live driver. Current validation used zero hosted
inference requests and one real catalogue request.

## Browser mission fixture transport

`probe.js --runtime-bundle <owned-bundle-directory> --mission-transport B02`
prepares a synthetic real-runtime smoke against a host-owned orders fixture.
B01, B02, B03 and M02 are the supported HTTP contracts. The explicit Run step
opens the fresh Sandbox; preparation opens nothing and calls no provider.

This contract uses at most 4,096 shared fixture/provider messages, 64 MiB
aggregate transport bytes, 2 MiB exchange files and 1 MiB decoded bodies. The
older smoke keeps its 32-message/16-MiB default. Paid request caps are separate;
provider request identities may exceed 32 when earlier messages served fixtures.

Only declared routes/methods/filter names are forwarded to the controller-owned
loopback portal. Its state and correction/commit checkpoints remain outside the
guest. The sole forwarded attachment header is the fixed `orders.csv` filename.
Intent is logged before an effect, state/response hashes afterward; publication
failure cannot repeat a completed mutation. Inspection matches immutable framed
bytes with the unmapped host fixture ledger. HTTP activity alone remains
`browser_interaction: unobserved`; live integration must supply independent
browser observations before those outcome criteria can pass.

Local controls exercise four actual browser workflows, including CSV download.
The actual guest smoke checks navigation/runtime/transport and process cleanup.
It uses a fake model and does not report agent intelligence or unlock core live
dispatch. Bounded artifact export and full isolated workflow orchestration remain
pending.

## Protected actor and bounded artifact export

`probe.js --runtime-bundle <owned-bundle-directory> --actor-probe` prepares the
protected actor control. Explicit Run opens a fresh guest and uses a scripted
fake provider. The real Zeus app, Python and managed browser run under the
standard account; the collector and intermediate report stay private. Its key
is pinned before startup. Profile paths come from the actual user token.

After normal execution, the controller stops the account/processes and snapshots
the declared input/output files. The signed result binds the export hash. The
host validates the job/nonce/names/hashes and retains bytes without loading them
as code or HTML. The generic artifact channel permits at most 64 flat names,
2 MiB per file and 8 MiB encoded total. Missing artifacts remain missing; links,
device names, stale packets and changed bytes are rejected. Public actor input
packets are available for all twelve missions, including the initial SQLite DB.

This is a runtime/export prerequisite, not a model benchmark run. Core paid
dispatch remains gated until complete isolated workflow/provider integration.
The synthetic probe's short timeout is not the full mission's execution budget.
Native process status uses a retained handle to avoid intermittently blank
PowerShell exit-code properties; running status and actual exit 259 are distinct.
